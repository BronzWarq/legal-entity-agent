# legal-entity-agent

ИИ-агент для проверки сведений о юридических лицах по ИНН, ОГРН, КПП и другим реквизитам через официальный веб-сервис ФНС. Репозиторий является отдельным проектом и не связан с `telegramm-bot`.

## Что подготовлено

- проверка контрольных сумм ИНН и ОГРН до отправки запроса;
- приём КПП, названия, адреса и нескольких реквизитов в одном запросе;
- клиент публичного сервиса ЕГРЮЛ/ЕГРИП ФНС;
- консервативное распознавание признаков недостоверности;
- отчёт с источником и временем проверки;
- CLI-команда `legal-entity-check`;
- Telegram-бот с командами `/start`, `/help`, `/check` и `/check_all`;
- Excel-отчёт после одиночной и массовой проверки;
- автоматическая реакция выбранным эмодзи на сообщения доверенных пользователей;
- русскоязычный режим общения с обращением к боту «Налог»;
- необязательный разговорный ChatSkill через OpenAI Responses API;
- необязательная расширенная проверка контрагента через `atomno-mcp-fns-check`;
- история сохранённых проверок через `/history`;
- проверка пользователя в каждом чате по Telegram user ID и тегу;
- Главный администратор `@Sholomon` с правами управления доступом;
- команды `/grant`, `/revoke` и `/trusted` для выдачи, отзыва и просмотра прав;
- команда `/skills` с кратким описанием возможностей агента;
- журнал запросов и обратной связи для контролируемого обучения;
- команды администратора для проверки очереди и экспорта одобренных примеров;
- тесты для идентификаторов, разбора ответа ФНС, прав доступа и контура обучения.
- проверка лицензий по естественной фразе «Налог, проверь лицензию…»;
- локальный реестр лицензий, контроль сроков и `/license_monitor`;
- список компаний для мониторинга через `/watch`, `/unwatch`, `/watched`;
- объяснение сохранённого результата через `/why`;
- импорт CSV/XLSX с дедупликацией, прогрессом и массовой Excel-выгрузкой;
- аудит административных действий через `/audit`.

## Постоянное обучение на запросах

Агент не меняет рабочую логику автоматически по одному сообщению. Каждый
успешный или неуспешный запрос Telegram-пользователя записывается в локальную
SQLite-очередь. Пользователь может нажать кнопку **«Верно»**, **«Ошибка»** или
**«Проверить»** либо отправить команду:

```text
/feedback ID correct|incorrect|needs_review [комментарий]
```

Администратор просматривает очередь и принимает решение:

```text
/learning_queue
/learning_review ID approved|rejected [исправленный ответ]
/learning_export
```

В экспорт попадают лишь записи, одобренные администратором. Полученный JSONL
используется для отдельного анализа, корректировки правил разбора или обучения
модели через новую проверяемую версию кода. Такой процесс предотвращает
автоматическое закрепление ошибочного или намеренно искажённого ответа.

По умолчанию в журнале не сохраняются исходные реквизиты и полный текст ответа:
вместо них записываются HMAC-отпечатки и технические признаки результата.
Сохранение исходных данных включается явно через `LEARNING_STORE_RAW_REQUESTS=true`
после утверждения правил хранения и доступа к данным. Идентификаторы Telegram
пользователей также сохраняются в виде отпечатков.

## Важное ограничение

Сервис `egrul.nalog.ru` является веб-интерфейсом ФНС, а не заявленным стабильным API. Код не обходит CAPTCHA, антибот-защиту или авторизацию. Если ФНС изменит формат ответа или запросит CAPTCHA, проверка возвращает ошибку и не делает вывод об отсутствии недостоверности.

## Расширенная проверка контрагента

В проект добавлен необязательный адаптер к [atomno-mcp-fns-check](https://github.com/atomno-mcp/mcp-fns-check)
(MIT). Он дополняет основной результат ФНС агрегированным отчётом по открытым
источникам: жизненный статус, банкротство, налоговые долги из выгрузки ФНС,
массовый адрес/руководитель, дисквалификация, ФССП и арбитражные дела.

Подключение выполняется явно:

```bash
pip install -e ".[bot,deep-check]"
```

и в `.env`:

```env
MCP_FNS_CHECK_ENABLED=true
MCP_FNS_CHECK_EXTENDED_RISKS=true
MCP_FNS_CHECK_LAWSUITS_THRESHOLD_RUB=1000000
```

Расширенный слой запускается только для запроса с одним ИНН или ОГРН. Его
вердикт не заменяет проверку отметки о недостоверности в живом ЕГРЮЛ. Если
ЕФРСБ, ФССП, КАД или другой источник недоступен, в отчёте показывается ручная
проверка/неопределённый риск, а не отсутствие риска. Ошибки расширенного слоя
не блокируют базовый ответ ФНС.

По умолчанию адаптер заменяет дисковый кэш upstream на одноразовый кэш в
памяти: сырые ответы ФНС не записываются в SQLite. Локальные реестры upstream
(если они загружены отдельно) остаются отдельными структурированными данными и
должны обновляться по правилам исходного проекта.

Отдельно важно различать:

- **«недостоверность обнаружена»** — в полученном ответе есть соответствующая отметка;
- **«недостоверность отсутствует»** — ответ ФНС содержит явное указание на отсутствие такой отметки;
- **«не распознано»** — в ответе нет достаточного явного признака, поэтому агент не делает предположение.

## Форматы запроса

Разрешённые пользователи могут отправлять один запрос с одним или несколькими
реквизитами:

```text
/check ИНН 7707083893
/check ОГРН 1027700132195 КПП 770401001
/check ООО Ромашка Москва Тверская 1
```

ИНН и ОГРН проходят проверку контрольной суммы, КПП — проверку длины в девять
цифр. Название, адрес и иные данные передаются как свободный поисковый текст.
Сервис ФНС может вернуть несколько совпадений, поэтому результат необходимо
сверять с официальной выпиской.

## Русскоязычное обращение «Налог»

Бот понимает свободные сообщения, начинающиеся с имени **«Налог»**. Он
извлекает из фразы намерение и данные для проверки, после чего применяет те же
проверки контрольных сумм, ограничения доступа и сохранение истории, что и
команда `/check`.

Примеры:

```text
Налог, проверь компанию с ИНН 7707083893
Налог, мне нужно проверить компании со следующими данными: ИНН 7707083893 КПП 770401001
Налог, проверь ООО Ромашка, Москва
Налог, покажи историю проверок
Налог, проверь все компании
Налог, проверь лицензию компании с ИНН 7707083893
```

Для лицензий используется отдельный реестр `LICENSE_DB_PATH`. Проверка по ИНН
сначала выполняет обычное определение юридического лица, затем ищет записи
лицензий в этом реестре. Отсутствие записи не является выводом об отсутствии
лицензии: источник лицензий должен быть официально подключён или запись должна
быть подтверждена администратором через `/license_add`. Сроки контролируются
командой `/license_monitor 30`.
Список компаний для будущих повторных проверок ведётся командами `/watch`,
`/unwatch` и `/watched`. Фоновый планировщик проверяет этот список с интервалом
`MONITOR_INTERVAL_SECONDS` и отправляет сообщение при изменении полученного
снимка; ошибки источника не превращаются в уведомления «рисков нет».

Команда `/app` открывает опубликованный Mini App при заданном `MINI_APP_URL`.
Mini App передаёт запрос обратно боту, поэтому права пользователей и правила
обработки остаются теми же, что и у обычных команд.
Реквизиты в интерфейсе Mini App не сохраняются в `localStorage`; постоянный
список мониторинга хранится на стороне бота и защищён теми же правами чата.

Проверка и массовая проверка по-прежнему доступны лишь пользователям с
разрешением в текущем чате, а `/check_all` и фраза «проверь все компании» —
Главному администратору `@Sholomon`. Распознавание работает локально по
контролируемым правилам, без передачи пользовательских сообщений стороннему
ИИ-сервису; это снижает риск ошибочного действия и утечки реквизитов.

## Разговорный ChatSkill

Если нужно вести свободный диалог, можно включить необязательный
`ChatSkill`. Он отвечает на сообщения, обращённые к «Налогу», которые не
распознаны как команда проверки, истории или массового запуска. Память
диалога хранится в оперативной памяти процесса отдельно для каждого чата и
пользователя. Команда `/chat_reset` очищает такую память.

Для включения задайте в локальном `.env`:

```text
OPENAI_API_KEY=...
OPENAI_MODEL=...
```

Внешнее приложение не использует личную веб-сессию ChatGPT, пароль или
cookies. Нужен отдельный API-ключ платформы; он не должен попадать в GitHub.
Без ключа бот продолжает работать в локальном режиме, а проверки ФНС и права
доступа не меняются. Свободные сообщения, переданные в ChatSkill, отправляются
выбранному API-провайдеру, поэтому перед промышленным включением нужно
утвердить правила обработки конфиденциальных данных.

## История проверок

После успешной проверки структурированный итог сохраняется в отдельную базу
данных. Команда `/history` показывает последние проверки текущего чата, а
`/history ID` выводит сохранённый отчёт. Обычный пользователь видит свои
запросы, а `@Sholomon` — историю всех пользователей текущего чата.

Главный администратор `@Sholomon` может запустить `/check_all` (также
доступны записи `/checkall` и `/check all`). Команда выбирает уникальные юридические лица
из всей базы `HISTORY_DB_PATH`, повторно отправляет сохранённые запросы в
ФНС и сохраняет новые результаты в историю текущего чата. Уникальность
определяется по ИНН/ОГРН, а для записей без распознанных реквизитов — по
исходному тексту запроса. В итоговом сообщении показываются успешные и
неуспешные проверки с идентификаторами, по которым можно открыть подробный
отчёт через `/history ID`. Число параллельных запросов задаётся
`CHECK_ALL_CONCURRENCY` (по умолчанию — 3).

После успешной одиночной проверки бот отправляет текстовый результат и файл
Excel. При `/check_all` после завершения массовой операции отправляется один
файл со всеми проверенными юридическими лицами. В таблице четыре столбца:

1. Номер;
2. Наименование юридического лица;
3. ИНН, ОГРН, КПП и иная информация для поиска;
4. Есть или нет недостоверности.

Команда `/why ID` показывает сохранённые источники, время проверки, маркеры
недостоверности и полный отчёт без нового запроса к ФНС. CSV/XLSX можно отправить
боту с подписью `/bulk` или «проверить файл». Строки дедуплицируются,
обрабатываются параллельно с ограничением `BULK_CONCURRENCY`, бот показывает
прогресс и отправляет итоговый Excel. Максимальный размер задаёт `BULK_MAX_ROWS`.

## Лицензии, роли и аудит

Главный администратор может добавить подтверждённую запись:

```text
/license_add НОМЕР ИНН ДД.ММ.ГГГГ [примечание]
/license 7707083893
/license_list
/license_monitor 30
/audit
```

`/audit` доступна `@Sholomon` и сохраняет технические действия без сырых
ответов ФНС. Роли выдаются отдельно для каждого чата:

```text
/grant @username viewer
/grant @username checker
/grant @username reviewer
/grant @username manager
```

`viewer` может просматривать результаты, `checker` запускает проверки,
`reviewer` дополнительно работает с обратной связью, `manager` получает полный
рабочий доступ без права менять ACL. Корневой администратор `@Sholomon` не
изменяется.

## Telegram-бот

1. Создайте бота через `@BotFather`.
2. Заполните `BOT_TOKEN` в `.env`.
3. Задайте непредсказуемую стабильную `LEARNING_HASH_SALT` и запустите `legal-entity-bot`.
   При пустом значении бот останавливается до начала обработки сообщений.

Если VPS не может напрямую подключиться к Telegram API, задайте прокси в `.env`:

```env
TELEGRAM_PROXY=socks5://user:password@proxy.example:1080
```

Поддерживаются HTTPS/HTTP и SOCKS5-прокси. Значение содержит секрет доступа и не
должно попадать в GitHub. После изменения `.env` перезапустите бота.

Главный администратор во всех чатах — `@Sholomon`. Другим пользователям доступ
выдаётся отдельно в каждом чате:

```text
/grant @username
/revoke @username
/trusted
```

Команды можно выполнять ответом на сообщение пользователя. `/grant` и `/revoke`
доступны лишь `@Sholomon`; обычный доверенный пользователь может выполнять
проверки, но не может раздавать права, отзывать доступ или просматривать очередь
обучения. Для уже выданных прав сохраняется Telegram `user_id`, поэтому смена
username не даёт другому аккаунту получить доступ.

При выдаче доступа ответом на сообщение пользователя сохраняется его Telegram
`user_id`; это не позволяет получить доступ другому аккаунту после смены username.

## Реакции

Бот может автоматически ставить реакцию на сообщения пользователей, которым
выдан доступ в текущем чате. Telegram разрешает обычному боту одну реакцию на
сообщение. Доступны все стандартные реакции Telegram; настройки находятся в
`.env`:

```env
REACTIONS_ENABLED=true
REACTION_EMOJIS=all
REACTION_MODE=random
REACTION_CUSTOM_EMOJI_ID=
```

`REACTION_EMOJIS=all` включает полный текущий набор стандартных реакций для
обычных пользователей. Можно указать один или несколько эмодзи через запятую,
а `REACTION_MODE=single` будет использовать первый из них, `random` — выбирать
один случайный для каждого сообщения. Старый параметр `REACTION_EMOJI` также
поддерживается для обратной совместимости.

`REACTION_CUSTOM_EMOJI_ID` предназначен для custom emoji и сработает, если этот
идентификатор уже есть среди реакций сообщения либо разрешён администраторами
чата. Платные реакции бот использовать не может. Чтобы отключить реакции,
установите `REACTIONS_ENABLED=false`. В группе Telegram у бота должно быть
разрешено право реагировать на сообщения; если право запрещено, ошибка реакции
не останавливает обработку команд и проверок.

## Тесты

```bash
pytest
ruff check src tests
```

В проекте используется версия `0.12.1`. Перед публикацией выполняются тесты,
компиляция исходников, проверка зависимостей через `pip check` и статический
анализ Ruff.

Живой запрос к ФНС не включён в автоматические тесты: такие запросы могут зависеть от CAPTCHA, сетевых ограничений и текущего формата официального веб-интерфейса. Перед промышленным запуском требуется отдельный smoke-тест на разрешённом доступе и ручная сверка результата с выпиской ФНС.
