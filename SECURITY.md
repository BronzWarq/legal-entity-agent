# Security model

Проект использует защиту в несколько слоёв. Ни один отдельный механизм не
считается достаточным для авторизации:

1. Telegram `initData` проверяется на сервере по HMAC и ограничивается по
   сроку действия.
2. Каждая кнопка API Mini App получает короткоживущий launch-контекст,
   связанный с исходным чатом. `chat_id` из браузера не определяет права.
3. Каждый запрос получает уникальный `request_id`; повтор такого запроса
   отклоняется.
4. Действия, поля, размеры списков, частота и параллелизм ограничены.
5. Права проверяются повторно в обработчике каждого действия.

## Обязательные настройки

В рабочем `.env` должны быть заданы:

```env
BOT_TOKEN=...
MAIN_ADMIN_USER_ID=...
LEARNING_HASH_SALT=...
```

`@Sholomon` — отображаемая учётная запись; авторизация Главного
администратора выполняется по числовому Telegram `user_id`.

## Граница VPS

API должен слушать только `127.0.0.1:8081`. Наружу публикуется только Nginx
по HTTPS. Шаблоны для Nginx и systemd находятся в `deploy/` и требуют проверки
на конкретной конфигурации VPS перед применением.

## Аварийное отключение

Если обнаружена подозрительная активность:

1. временно остановить `legal-entity-bot` или убрать `MINI_APP_API_URL` из
   рабочего `.env` и перезапустить сервис;
2. при риске раскрытия токена перевыпустить `BOT_TOKEN` через BotFather и
   заменить его только на VPS;
3. после запуска старые launch-контексты будут недействительны;
4. проверить `/audit`, права чатов и журналы Nginx без раскрытия заголовка
   `X-Telegram-Init-Data`;
5. сохранить резервные копии SQLite-баз до удаления или очистки данных.

Нельзя записывать в GitHub, журналы или сообщения `BOT_TOKEN`,
`X-Telegram-Init-Data`, SMTP/API-ключи и содержимое `.env`.
